# 로또 통계 6/45

동행복권 로또 6/45의 역대 전 회차 데이터를 분석하는 통계 대시보드이자 번호 추첨기입니다.
1회(2002.12.07)부터의 공식 추첨 결과가 내장되어 있어 서버 없이 완전 오프라인으로 동작합니다.

**이 프로젝트는 당첨을 예측하거나 보장하지 않습니다.** 오히려 그 반대를 보여주기 위해 만들었습니다.

## 무엇이 다른가

일반적인 로또 앱은 "고빈도 번호"나 "미출현 번호" 같은 추천을 근거 없이 제시합니다.
이 프로젝트는 그런 방식들이 실제로 작동하는지를 **전수 계산과 아웃오브샘플 검증으로 직접 검정**하고,
그 결과를 앱 안에 그대로 공개합니다.

각 추첨 모델을 선택하면 그 모델이 어떤 가정 위에 서 있는지, 그 가정이 실제 데이터에서
어떻게 검정되었는지가 함께 표시됩니다.

## 검정 결과 요약

**추첨은 통계적으로 깨끗합니다.** 균일성 검정 χ²=28.59 (p=0.965), 직렬상관 p=0.268,
이상 쌍 2/990개(무작위 기대 2.7개), 재출현 간격 분산 49.59(이론 48.75), 주기성 신호 없음.
조작의 흔적이 남을 만한 다섯 지점을 모두 확인했지만 전부 비어 있었습니다.

**번호 선택으로 당첨 확률을 바꿀 수 없습니다.** 8,145,060개 조합 전수 계산 결과,
어떤 조합을 고르든 등수별 확률은 소수점 끝까지 동일합니다. 이것은 통계가 아니라 산술입니다.
정확히 k개가 일치하는 추첨결과의 개수는 항상 C(6,k)×C(39,6−k)이고, 이 식에 티켓 내용은 들어가지 않습니다.

**예측을 시도한 모델은 무작위보다 나빴습니다.** 934회 워크포워드 검증(회차 n을 예측할 때
1~n-1회 정보만 사용, 총 186,800게임)에서 빈도 기반 모델들은 완전 무작위 대비
통계적으로 유의하게 낮은 성적을 냈습니다. 특정 번호대에 게임이 몰리면서
게임끼리 같이 맞고 같이 틀리기 때문입니다.

**작동하는 레버는 두 개뿐이고, 둘은 서로 맞바꿔야 합니다.**
- *배치*: 여러 게임을 살 때 번호가 겹치지 않게 배치하면 "적어도 하나 당첨" 확률이 오릅니다.
  5게임 기준 +3.3%. 단 45÷6=7이라 7게임까지만 유효합니다. **기대 회수율은 바꾸지 못하고
  분산만 줄입니다.**
- *분배*: 사람들이 덜 고르는 번호를 쓰면 당첨 시 나눠 갖는 인원이 줄어 실수령액이 오릅니다.
  **기대 회수율을 실제로 올리는 유일한 레버입니다.**

회차별 인기도를 번호별로 분해하면 1~12(0.190) > 13~31(0.156) > 32~45(0.137) 순입니다.
흔히 말하는 생일 편향이 실재하며, 31 이하 전체가 32~45보다 선호됩니다.
가장 비인기인 32~45만 쓰면 수령액이 x1.164가 되지만, 14개뿐이라 겹치지 않는 배치가
2게임까지로 줄어 5게임 기준 "적어도 하나 당첨" 확률이 완전분리 대비 -12.1%가 됩니다.
기본 추천 모델은 **수령액 쪽을 택했습니다** — 덜 자주 당첨되지만 당첨되면 더 많이 받습니다.

어느 쪽을 택하든 기대 회수율은 여전히 마이너스입니다.

## 기능

- 최근 회차 당첨 번호, 1등 당첨금·당첨자 수
- 역대 누적 번호별 출현 빈도, 구간 분포, 상·하위 번호
- 9가지 추첨 모델 (각 모델의 가정과 검정 결과 포함)
- 뽑은 번호를 과거 전 회차와 대조하는 백테스트
- 홈 화면 설치(PWA), 완전 오프라인 동작
- 홈 화면 추가 안내 — 아이폰·안드로이드 탭, 브라우저별 단계 안내, 인앱 브라우저 감지

## 실행

정적 파일이라 별도 빌드가 필요 없습니다.

```bash
npx serve .
```

## 배포

**Vercel** — 프레임워크는 Other, 빌드 명령과 Output Directory는 비워둡니다.

```bash
vercel --prod
```

**GitHub Pages** — Settings > Pages에서 브랜치를 지정하면 바로 배포됩니다.
모든 경로가 상대 경로라 하위 디렉터리에서도 정상 동작합니다.

PWA 설치는 HTTPS에서만 동작하므로 `file://`로 직접 열면 설치와 오프라인 기능이 작동하지 않습니다.

## 데이터 갱신

매주 일요일 GitHub Actions가 동행복권 공식 데이터에서 새 회차를 받아 자동 반영합니다
(`.github/workflows/update-draws.yml`). 손으로 돌리려면 아래를 실행합니다.

```bash
node tools/update-draws.mjs --dry-run   # 받아서 검증만
node tools/update-draws.mjs             # 실제 반영
```

스크립트는 `RAW`의 마지막 회차 다음부터 조회해 이어붙이고 `sw.js`의 `CACHE`를 올립니다.
새 회차가 없으면 아무것도 하지 않으므로 몇 번을 돌려도 안전합니다.

받은 값은 그대로 믿지 않고 검증합니다. 번호 6개가 1~45 범위에서 중복 없이 나왔는지,
보너스가 당첨번호와 겹치지 않는지, 회차가 끊기지 않고 이어지는지, 추첨일이 토요일이고
앞 회차보다 뒤인지, 1등 총액이 1인당 상금 × 당첨자 수와 맞는지를 봅니다. 하나라도
어긋나면 **한 건도 반영하지 않고** 실패로 끝냅니다. 추첨 결과는 지어낼 수 없는 값이라
의심스러우면 반영하지 않는 쪽이 옳습니다.

`RAW` 형식은 `[회차, [번호6개], 보너스, "YYYY-MM-DD", 1등상금, 1등당첨자수]` 입니다.

**자동으로 따라오는 것** — 번호별 출현 빈도, 구간 분포, 상·하위 번호, 쌍 동시출현,
후행 출현, 균일성 검정(기대출현수·표준편차·카이제곱·p값), z-score, 소진 조합 비율.
전부 `RAW`의 순수 함수라 로드할 때마다 다시 계산합니다. 손댈 것이 없습니다.

**검정 결과도 함께 갱신됩니다.** 회귀·순열검정·주기성 등 `P`에 들어가는 값은
`tools/build-stats.mjs`가 공식 데이터에서 다시 계산합니다. 워크플로가 새 회차를 받은 뒤
이어서 돌리므로, 앱의 검정 결과는 항상 화면에 표시된 회차 수와 같은 기준입니다.

```bash
node tools/build-stats.mjs --dry-run   # 계산해서 보여주기만
node tools/build-stats.mjs             # index.html의 P 교체
```

순열검정은 난수를 쓰지만 시드를 고정해서, 같은 데이터면 항상 같은 `P`가 나옵니다.

`P`에서 유일하게 데이터와 무관한 것은 `m8`입니다. C(45,6)=8,145,060 전수 계산에서
나오는 조합론 상수라 회차가 늘어도 변하지 않습니다.

### 검정 방법

등수별 당첨자 수는 그 회차에 몇 장이 팔렸는지에 거의 비례하고, 판매량은 20여 년 사이
수십 배로 변했습니다. 당첨자 수를 그대로 평균 내면 시간 추세가 섞이므로 회차마다

```
인기비율 = 실제 당첨자 수 / (판매 게임 수 × 등수별 당첨 확률)
```

를 만들어 씁니다. 이 값이 1보다 크면 그 회차 당첨번호를 사람들이 평균보다 많이 고르고
있었다는 뜻이고, 판매량 효과는 분모에서 상쇄됩니다. 회귀는 이 인기비율에 대해 돌리며,
유의성은 t값과 순열검정 양쪽으로 확인하고 표본을 앞뒤로 갈라 각각 재현되는지도 봅니다.

## 고지

본 서비스는 통계 참고용 도구이며 복권 판매·구매 기능이 없습니다.
어떤 방식도 1등 당첨 확률 1/8,145,060을 바꾸지 못합니다.
복권 구매는 만 19세 이상만 가능합니다.
